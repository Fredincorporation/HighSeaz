# HighSeaz — Architecture & Interfaces

## Repo / workspace layout (target)

npm workspaces at repo root; the existing Next app stays as the client.

```
HighSeaz/
├─ package.json            # workspaces: client, server, contracts, shared
├─ src/                    # CLIENT (Next.js + Babylon). Keep template files.
│  ├─ app/                 #   page.tsx boots Engine/Scene/Havok + loads editor scene
│  ├─ game/                #   CODE-FIRST runtime (the real game):
│  │  ├─ ocean.ts          #     Ocean/Water/Sky material + weather-as-gameplay hooks
│  │  ├─ ship/             #     ship entity, input, wind/sailing physics, follow camera
│  │  ├─ combat/           #     cannons, ballistic projectiles, hit resolution (view only)
│  │  ├─ net/              #     WebSocket client, snapshot ingest, interpolation/prediction
│  │  ├─ ui/               #     Babylon GUI: HUD, docking menu, bounty board, auction
│  │  ├─ identify/         #     own / alliance / NPC ship markers above meshes
│  │  └─ wallet/           #     viem/wagmi + WalletConnect; read ships/balance; write txs
│  ├─ scripts/             #   editor IScript components (scene-object behaviors)
│  └─ scripts.ts           #   scriptsMap (generated by Babylon Editor)
├─ server/                 # AUTHORITATIVE Node game server (ws + tick loop) — NOT Next routes
├─ relayer/                # (or inside server) batches async on-chain writes; owns hot wallet
├─ contracts/              # Foundry project (see interfaces below)
├─ shared/                 # wire-protocol TS types + contract ABIs, imported by client & server
├─ public/scene/           # generated .babylon scene (camera/lights/sky) via editor `pack`
└─ assets/                 # Babylon.js Editor project (GLB/models, materials, env)
```

Decision: mostly code-first. The Babylon Editor `pack` step is a friction point for a procedural + network-spawned world; keep the editor only for lighting/sky/camera polish, build ocean/ships/net in `src/game/`.

## Netcode model

- Server-authoritative. Client sends **inputs** (rudder, sail trim, aim, fire); server simulates and broadcasts **state snapshots**.
- Tick rate 20–30Hz; delta/AOI by region so clients only get nearby ships.
- Client-side **prediction** for own ship heading/position; **interpolation** for remote ships; **reconciliation** on server correction.
- Ship ownership of the sim: server resolves damage, sinking, cargo transfer, loot, faction rep — never trust the client for combat/loot outcomes.
- Single bounded sea region per server process for the demo. Meshing is a roadmap concept (tile grid + ownership), NOT built.
- One player controls one active ship; additional owned ships run server-side auto-mode AI and are broadcast like NPC ships.
- Shared types in `shared/` are the single source of truth for message shapes; client and server must not drift.

## On-chain vs off-chain data model (hard line)

- **On-chain state:** ship ownership + provenance (ERC-721), rare loot tokens, active bounty pots, open/ended auctions + settlement, alliance membership (for trustless bounty exclusion).
- **Off-chain (Postgres + Redis):** live positions, velocity, hull HP, cargo manifest & counts, repair state/timer, faction reputation, POIs, region/instance assignment, social/alliance graph edges, chat.
- **Settlement flow:** server emits signed intents → relayer calls contracts (mint loot on sink-win, settle auction/bounty). Gameplay never waits on finality.

## Contracts (Foundry + OpenZeppelin). Apply solidity-security + property-based-testing.

`ShipNFT` (ERC-721)
- `mint(address to, ShipClass class, ...) returns tokenId` — purchase is USDG-in via `ShipStore`.
- state: `active | sunk(needs repair) | auto | listed`; sunk is a status, NOT burn (hull persists).
- provenance (on-chain, incremented by trusted server/relayer): `uint kills; uint bountiesSurvived; uint sunkAndRepaired;`
- only game-server role can mutate live-derived fields; ownership transfers are player-signed.

`ShipStore` (marketplace, buy-only)
- sells ships + market goods for USDG (USDC6 decimals → handle decimals explicitly). Players CANNOT sell here.

`BountyEscrow`
- `declare(uint tokenId, uint usdgAmount)` — pulls USDG, locks a pot against a specific ship tokenId.
- `claim(uint tokenId, address winner)` — called by trusted server when that ship is sunk.
- Invariants: winner ∉ declarer's alliance AND winner ≠ declarer (read `AllianceRegistry`); pot fully drained exactly once (first sink wins); no double-claim; safeERC20 receive checks.
- Supports "bounty chains": a new declare can target the previous winner's ship.

`AllianceRegistry`
- membership set per allianceId so `BountyEscrow` can verify exclusion trustlessly. `create/join/leave/allianceOf(address)`.

`AuctionHouse`
- player→player listing of items/rare loot for USDG; `list/bid/cancel/settle`. Checks-effects-interactions; refund on outbid; no zero-value sniping window assumptions.

`LootMint` (ERC-20/ERC-1155 as appropriate)
- mints rare loot to winner wallets on sink/raid events. Ordinary cargo stays off-chain.

USDG token:
- Confirmed **Arbitrum One mainnet** USDG = `0x004B506865409877C9fA29bfb1ebA929984B9bbC` (reference only). On **Robinhood Chain testnet** the address differs — deploy a **mintable USDG mock** for the demo and swap the real testnet address when known. Do not hardcode mainnet in testnet config.

## Demo vertical slice (9 days — what must run live)

1. Bounded sea region, one server, 2–5 concurrent players syncing.
2. Own ship (wind sailing + cannons) vs another player / NPC; sink it → cargo transfers to victor.
3. Live on-chain: declare bounty → sink target → **USDG bounty lands in winner's wallet** on Robinhood Chain; ship NFT mint/transfer visible.
4. Docking UI menu (buy ship / repair / bounty board / auction) at a port proximity.
5. Own vs alliance vs NPC ship markers readable on screen.
